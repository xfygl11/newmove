# 01 · 项目概述与借鉴分析

> 本文档是整个项目的决策起点，说明「做什么」「借鉴什么」「用什么技术」「哪些点需要先拍板」。

---

## 1. 项目定位

开发一款**手机 APK（Android 本地端）**，把「AI 写小说」与「小说 → 动漫」两条链路整合为一个 App，覆盖以下五个核心能力：

| 序号 | 能力 | 说明 |
|---|---|---|
| 1 | AI 写小说 | 从创意/设定出发，AI 辅助生成大纲、世界观、角色、逐章正文，支持续写、润色、审校 |
| 2 | 小说改写动漫剧本 | 把小说文本结构化改编为可制作的动漫剧本（场次、动作、对白、声音） |
| 3 | 提取剧本骨架 | 从剧本中抽取结构化骨架：场景、角色、道具、节拍、分镜信息 |
| 4 | 生成动漫资产图片 | 生成角色（三/四视图参考板）、场景（主视图）、道具（多视图板）图片 |
| 5 | 生成动漫镜头 | 基于骨架与资产生成分镜画面 / 视频片段 |

**关键约束（用户已明确）：**

- 目标是**手机 APK**，不是电脑端 + 服务器端。
- **不使用本地 AI 模型**，全部通过**云端 AI API 端点**完成（LLM 文本、文生图、图生图、文/图生视频）。
- 数据**本地存储**，不上传云端服务器（仅 API 调用会发送必要的提示词/参考图到所选模型供应商）。
- 流程与 Agent/技能（skills）设计**认真借鉴开源项目 [Toonflow](https://github.com/HBAI-Ltd/Toonflow-app)**。
- AI 写小说部分**调研借鉴 GitHub 相关开源项目**（本文档选 [InkOS](https://github.com/Narcooo/inkos) 为主参考）。

## 2. Toonflow 借鉴分析

### 2.1 项目概况

Toonflow 是一站式 AI 短剧/漫剧创作平台，技术栈为 **Electrobun + Vue 3 + TypeScript + Bun**（monorepo；桌面壳 `apps/desktop` 使用 electrobun 2.0，服务端 `apps/server` + Web 端 `apps/web`）。核心是「无限画布 + Agent + 可视化节点工作流」，把「小说/剧本 → 资产 → 分镜 → 图片/视频」全流程放进同一张画布。

### 2.2 借鉴它的分层 Agent 职责

Toonflow 没有显式命名「三层架构」，但从 `workflow/SKILL.md`（提示词决策与执行硬隔离）和 `teams/storyboardTeam`（导演/编写/审阅分工）可以归纳出三层职责（本文归纳，非官方表述）：

| 层级 | 对应 Toonflow 实现 | 职责 | 权限边界（源码可证） |
|---|---|---|---|
| 决策层 | workflow/SKILL.md 主流程 + PART A | 理解意图、拆解任务、产出定稿提示词 | 「提示词硬隔离」：定稿前不碰画布，执行层不得改写已定稿的分段/剧情/站位/运镜 |
| 执行层 | storyboardTeam（导演→编写）+ canvasExecution.md | 文字分镜编写、连接真实参考、写入生成节点、启动媒体生成 | 只做委派工作；成员不递归互相委派；须先取得算力授权并「临执行复核」 |
| 监督层 | reviewer 成员 + 连续性知识 | 审阅产出、指明镜头/依据/最小修改建议 | 不代执行、不替用户批准生成、不调用消耗算力的工具、不改画布文件 |

> 对移动端的启示：**决策层 = 编排流水线的「主编排 Agent」，执行层 = 各阶段专职 Agent（编剧/导演/资产/分镜），监督层 = 审校 Agent**。移动端可以把这个协作关系简化为一条**有状态机的 Pipeline**，每个阶段一个专职 Agent。

### 2.3 借鉴它的 Skills（技能）体系

Toonflow 的「智能」本质上是一组 **Markdown 技能文件 + 工具调用**，核心在 `packages/skills/` 与 `packages/teams/`：

| 技能/文件 | 职责 | 对本项目的借鉴 |
|---|---|---|
| `workflow/SKILL.md` | 制作工作流主入口：输入判定 → 剧本 → 资产 → 分镜 → 生成 | **Pipeline 主流程** |
| `workflow/references/sourceAndScript.md` | 输入与剧本：小说改编、创意写剧本、定稿剧本提取 | **「小说 → 剧本」阶段** |
| `workflow/references/methods/storyDevelopment.md` | 故事开发：命题、人物、因果、代价选择 | **「AI 写小说」阶段（与 InkOS 结合）** |
| `workflow/references/methods/screenAdaptation.md` | 剧本改编：视听化、场景任务、对白、信息差、节奏 | **「小说 → 剧本」核心方法论** |
| `workflow/references/assets.md` | 资产：角色四视图板、场景主视图、道具 2×2 板 | **「资产图片」生成规范** |
| `workflow/references/methods/visualDesign.md` / `colorAndLight.md` | 视觉设计、色彩用光 | 资产与分镜画面风格 |
| `workflow/references/canvasExecution.md` | 画布执行、真实引用绑定、生成授权 | **「执行层」与算力授权** |
| `workflow/references/stateAndDelivery.md` | 状态与交付、版本记录 | **本地版本管理** |
| `canvas/SKILL.md` | 画布节点操作手册 | 移动端替换为**结构化数据操作** |
| `teams/storyboardTeam/` | 导演/编剧/审阅 + 连续性知识 | **分镜阶段的三角色协作** |

其中 `workflow/SKILL.md` 内嵌了 Seedance 视频导演的 **PART A 执行规则（A0–A12）**，是「剧本 → 分镜 → 视频提示词」的最核心方法论，要点：

- **A0 剧情保真锁**：只导演，不编剧。禁止新增/删除/替换/改归属/改顺序/改因果。
- **A1 资产命名与参考绑定**：角色/场景/道具用稳定标识，参考图绑定到每个生成段。
- **A2 全量节拍解析**：把剧情拆成完整、连续、可计时的原子节拍（对白/动作/反应/信息/过渡），全部登记，建立「源剧情账本」。
- **A3 分段与时长预算**：按对白自然语速 + 动作时间估算单段时长，先全片规划再分批交付。
- **A4 资产与出镜状态**：每个角色/场景/道具按时间轴登记出镜状态。
- **A5 站位双层坐标**：世界坐标（轴线地标）+ 画面坐标（当前机位），每段自包含。
- **A6 表演层**：情绪是行为的副产品，微表情必须有源剧情依据。
- **A7 运镜与段间衔接**：相邻独立生成段至少满足主体/景别/角度中一项差异，避免「错误续帧」。
- **A8 跨段连续性检查**：人物位置、道具状态链、场景物理环境连续性。
- **A9 分段提示词模板**：按模型路由输出最终可投喂的生成提示词。

### 2.4 借鉴它的 Provider 抽象

Toonflow 通过 `packages/providers/` 统一接入模型，核心发现：

- **LLM**：`protocol: "openai-completions"`（OpenAI 兼容协议，DeepSeek 等均走此协议）。
- **媒体**：图片/视频/音频供应商（tfRouter、apiMart、meta）。
- **AI 调用**：`apps/server/src/utils/ai/index.ts` 用 `@earendil-works/pi-ai` 做协议抽象（openai-completions / openai-responses / anthropic-messages），支持流式输出、多模态参考（图片 base64）。
- **Agent 运行时**：`apps/server/src/agent/runtime/subAgent.ts` 用 `@earendil-works/pi-coding-agent` 做 Agent 会话与子 Agent 委派。

> 对移动端的启示：**LLM 统一走 OpenAI 兼容 `/chat/completions` 协议 + SSE 流式**，这是移动端最容易对接的方式；图片/视频生成走各供应商的异步任务 API（提交任务 → 轮询/回调取结果）。移动端需要自建一个轻量 `ProviderAdapter` 抽象层，而不是依赖 `pi-ai` 这类 Node 库。

## 3. AI 写小说借鉴分析（InkOS 为主）

### 3.1 为什么选 InkOS

调研了多个 AI 写小说开源项目后，选定 **InkOS**（TypeScript，多智能体流水线）作为主要参考，理由：

- 它解决的核心痛点与本项目一致：**长篇创作的角色失忆、伏笔断线、文风突变**。
- 它把写作拆成可审计的工程化流水线（写手/审计员/修订员），而非「单次 prompt 生成一段文字」。
- 它有 **Truth Files（真相文件）** 机制，解决长期记忆/一致性。

同时参考其思路但**做移动端适配裁剪**（见第 5 节）。

### 3.2 InkOS 核心机制

**多智能体协作（README 官方职责表 + `src/agents/` 源码）：**

| Agent | 职责 |
|---|---|
| Radar 雷达（可插拔） | 扫描平台趋势和读者偏好，指导故事方向 |
| Planner 规划师 | 读取作者意图 + 当前焦点 + 检索结果，产出本章意图（must-keep / must-avoid） |
| Composer 编排师 | 按任务从结构化状态、控制文档和材料中选择上下文，记录保护层级、检索与压缩轨迹 |
| Architect 建筑师 | 建书/导入时生成基础设定：故事框架、规则、角色与长期控制文件 |
| Writer 写手 | 基于编排后的精简上下文生成正文（字数治理 + 对话引导） |
| Settler 状态结算 | 通过 typed tool 提交正文有证据的增量 state delta，由宿主校验并原子落盘 |
| 审稿 Agent | 对照用户意图、正典、状态、章节计划，返回有证据的定性观察 |
| Reviser 修订者 | 接受明确修改目标，生成并原子落盘新版本 |
| 连续性审计员 | 对照状态文件检查每章草稿的一致性（角色「记起」没见过的事、拿出已丢失的武器等） |

**真相与状态机制（`story/` 目录，源码可证）：**

| 层 | 内容 |
|---|---|
| 权威结构化状态 `story/state/*.json` | `current_state.json`（SPO 事实三元组，带生效章节区间 validFrom/validUntil 与来源章）、`hooks.json`（伏笔钩子：open/progressing/deferred/resolved/superseded 五状态 + 预期回收）、`chapter_summaries.json`（章节/人物/事件/状态变化/钩子活动/情绪/章节类型）、`manifest.json`；均经 Zod schema 校验 |
| 人类可读投影 `story/*.md` | `current_state.md`、`pending_hooks.md`、`chapter_summaries.md`、`character_matrix.md` 等（由权威 JSON 渲染，只读） |
| 控制文档 | `story/author_intent.md`（这本书长期想成为什么）、`story/current_focus.md`（近 1–3 章要把注意力拉回哪里） |
| 每章运行时 `story/runtime/` | `chapter-XXXX.intent.md`（本章目标/保留项/避免项）、`context.json` 与 `trace.json`（实际进入模型的上下文与编译轨迹） |
| 检索投影 `story/memory.db` | 可重建的 SQLite FTS5/BM25 索引，**不作为故事事实权威** |

关键设计：正文与状态作为同一组产物**原子落盘**；Settler 只提交有证据的增量 delta，代码层做 immutable apply；「资源/支线/情感弧线」等没有独立文件，统一用事实三元组（current_state）与摘要行（mood/chapterType）表达。

**Revision modes（修订模式，CLI 可证）**：`spot-fix`（定点修）、`polish`（润色）、`rewrite`（重写）、`rework`（结构重组）、`anti-detect`（去 AI 味，由可替换的 deslop Skill 提供）。

> 对本项目的启示：借鉴「权威 JSON 状态 + 人类可读投影 + 事实三元组带章节有效期 + typed delta 原子落盘」的思路，把它简化为**本地数据库状态表（本项目定义为 7 类：世界事实、角色矩阵、资源与道具、伏笔钩子、章节摘要、作者意图、当前焦点）**。写作时只注入相关片段；每章定稿后由固化步骤提交状态增量；审校时对照状态表查一致性。7 类的划分是本项目对 InkOS 机制的移动端裁剪。

## 4. 两套流程的整合方案

Toonflow 擅长「剧本 → 镜头」，InkOS 擅长「创意 → 小说」。整合后的完整链路：

```text
┌─────────────────────────────────────────────────────────────────┐
│                    创意 / 一句话 / 已有小说原文                    │
└──────────────────────────────┬──────────────────────────────────┘
                               ▼
                 ┌─────────────────────────┐
                 │  阶段 A：AI 写小说        │ ← 借鉴 InkOS
                 │  世界观 / 角色 / 大纲 /    │   Planner + Writer
                 │  逐章正文 / 审校 / 固化    │   + Truth Files
                 └────────────┬────────────┘
                              ▼
                 ┌─────────────────────────┐
                 │  阶段 B：小说 → 动漫剧本  │ ← 借鉴 Toonflow
                 │  结构化改编 / 视听化 /     │   sourceAndScript +
                 │  场次对白 / 忠实度检查     │   screenAdaptation
                 └────────────┬────────────┘
                              ▼
                 ┌─────────────────────────┐
                 │  阶段 C：提取剧本骨架     │ ← 借鉴 Toonflow A2
                 │  节拍 / 场景 / 角色 / 道具 │   全量节拍解析
                 │  分段 / 时长 / 出镜状态    │
                 └────────────┬────────────┘
                              ▼
                 ┌─────────────────────────┐
                 │  阶段 D：生成动漫资产图片  │ ← 借鉴 assets.md
                 │  角色四视图 / 场景主视图 / │   视觉设计 + 色彩用光
                 │  道具多视图               │
                 └────────────┬────────────┘
                              ▼
                 ┌─────────────────────────┐
                 │  阶段 E：生成动漫镜头     │ ← 借鉴 PART A A4-A9
                 │  分镜提示词 / 参考绑定 /    │   站位 / 表演 / 运镜 /
                 │  生成图片或视频            │   连续性 / 提示词模板
                 └─────────────────────────┘
```

各阶段都产出**可持久化、可编辑、可回溯**的结构化数据，用户可在任意阶段人工介入修改后继续。

## 5. 移动端适配裁剪（关键决策）

Toonflow 是桌面端无限画布 + 可视化节点，移动端必须裁剪：

| Toonflow 桌面能力 | 移动端裁剪方案 |
|---|---|
| 无限画布自由编排节点 | 改为**结构化列表/时间轴视图**（剧本 → 分镜 → 资产的线性流程 + 可点开编辑） |
| 可视化节点连线 | 改为**数据引用关系**（分镜引用资产 ID、参考图句柄），无需拖拽连线 |
| `canvas/SKILL.md` 画布工具 | 替换为**本地数据库 CRUD 工具**（Agent 直接读写结构化实体） |
| Agent 运行时 `pi-coding-agent` | 自建轻量 **Pipeline 编排器 + 阶段状态机**（移动端无 Node 运行时） |
| 文件系统工作区 | 本地 **SQLite + 文件目录**（资产图片存本地，元数据存 DB） |
| 模型供应商 `pi-ai` | 自建 **ProviderAdapter**（LLM 走 OpenAI 兼容 SSE，媒体走异步任务 API） |
| 桌面端 Electrobun 桌面壳（本地服务 + Web 视图） | 单进程移动 App（Dart/Flutter 或 Kotlin） |

**核心结论：移动端保留 Toonflow 的「Skills（Prompt 方法论）与流水线思想」，丢弃「画布/节点/桌面壳」，用本地数据库 + 结构化数据流替代。**

## 6. 技术选型

### 6.1 推荐：Flutter

| 维度 | 说明 |
|---|---|
| 平台 | Android APK 为主，未来可扩展 iOS，单代码库 |
| 语言 | Dart，强类型，适合复杂业务建模 |
| 状态管理 | Riverpod（推荐）或 Bloc |
| 本地存储 | Drift（SQLite ORM，类型安全）或 Isar；资产文件存应用私有目录 |
| 网络 | Dio + SSE 流式（LLM 流式输出） |
| 编辑器 | flutter_quill（富文本/Markdown 小说编辑器） |
| 图片 | cached_network_image（本地文件 + 网络图缓存） |
| 视频 | video_player（镜头预览） |
| 分镜展示 | 自绘 ListView/GridView + 可选时间轴 |

**选择理由：**
1. 移动端复杂 UI（编辑器、分镜列表、资产网格、流式对话）生态最成熟。
2. 单代码库覆盖 Android/iOS，符合「手机 APK 本地端」定位。
3. 状态管理与数据层能力强，适合本项目「多阶段流水线 + 结构化数据」的复杂度。
4. 性能优于 React Native，开发效率优于 Kotlin 原生。

### 6.2 备选方案

| 方案 | 优势 | 劣势 |
|---|---|---|
| Kotlin + Jetpack Compose | Android 原生性能最佳 | 仅 Android，开发效率略低 |
| React Native / Expo | 与 TS 参考项目技术栈一致 | 复杂编辑器/长列表性能、生态不如 Flutter |
| Flutter（推荐） | 见上 | 需学习 Dart |

> **技术栈已确认：Flutter。**

### 6.3 AI API 端点方案

- **LLM 文本**：OpenAI 兼容 `/v1/chat/completions`（支持 DeepSeek、通义、Kimi、智谱、OpenAI 等任意兼容端点），SSE 流式输出。
- **文生图 / 图生图**：优先选支持 OpenAI Images 兼容协议或 gpt-image 类供应商；也支持自定义异步任务供应商（提交 job → 轮询结果）。
- **文/图生视频**：借鉴 Toonflow 的 Seedance 接入思路，走供应商异步任务 API（提交 → 轮询），App 内做任务队列与结果回填。
- **用户自配**：App 内置「模型供应商配置」页面，用户填入 Base URL + API Key + 模型名，与 Toonflow 的 `customProviders` 机制一致。

## 7. 已确认的关键决策（用户拍板）

| 决策点 | 结论 |
|---|---|
| 技术栈 | **Flutter** |
| 镜头产物形态 | **分镜图 + 视频都要**（先出分镜图供确认，再对确认镜头生成视频） |
| AI 写小说自动化程度 | **人机协作**（每章生成后人工确认/修订再进入下一章） |
| 里程碑范围 | **直接含视频**（M0–M7 全部执行，视频为核心交付而非后置选项） |

> 影响：开发计划按「全量交付（含视频）」推进，M6 视频生成为核心里程碑；M5 分镜图仍是视频前必经的确认节点。
