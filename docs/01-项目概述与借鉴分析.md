# 01 · 项目概述与借鉴分析

> 本文档是整个项目的决策起点，说明「做什么」「借鉴什么」「用什么技术」「哪些点需要先拍板」。

---

## 1. 项目定位

开发一款**手机 APK（Android 本地端）**，把「AI 写小说」与「小说 → 动漫」两条链路整合为一个 App，覆盖以下五个核心能力：

| 序号 | 能力 | 说明 |
|---|---|---|
| 1 | AI 写小说 | 从创意/设定出发，AI 辅助生成大纲、世界观、角色、逐章正文，支持续写、润色、审校 |
| 2 | 小说改写动漫剧本 | 把小说文本结构化改编为可制作的动漫剧本（场次、动作、对白、声音） |
| 3 | 提取剧本骨架 | 从剧本中抽取结构化骨架：场景、角色、道具、节拍、分镜信息 |
| 4 | 生成动漫资产图片 | 生成角色（三/四视图参考板）、场景（主视图）、道具（多视图板）图片 |
| 5 | 生成动漫镜头 | 基于骨架与资产生成分镜画面 / 视频片段 |

**关键约束（用户已明确）：**

- 目标是**手机 APK**，不是电脑端 + 服务器端。
- **不使用本地 AI 模型**，全部通过**云端 AI API 端点**完成（LLM 文本、文生图、图生图、文/图生视频）。
- 数据**本地存储**，不上传云端服务器（仅 API 调用会发送必要的提示词/参考图到所选模型供应商）。
- 流程与 Agent/技能（skills）设计**认真借鉴开源项目 [Toonflow](https://github.com/HBAI-Ltd/Toonflow-app)**。
- AI 写小说部分**调研借鉴 GitHub 相关开源项目**（本文档选 [InkOS](https://github.com/Narcooo/inkos) 为主参考）。

## 2. Toonflow 借鉴分析

### 2.1 项目概况

Toonflow 是一站式 AI 短剧/漫剧创作平台，技术栈为 **Electrobun + Vue 3 + TypeScript + Bun**（monorepo；桌面壳 `apps/desktop` 使用 electrobun 2.0，服务端 `apps/server` + Web 端 `apps/web`）。核心是「无限画布 + Agent + 可视化节点工作流」，把「小说/剧本 → 资产 → 分镜 → 图片/视频」全流程放进同一张画布。

### 2.2 借鉴它的分层 Agent 职责

Toonflow 没有显式命名「三层架构」，但从 `workflow/SKILL.md`（提示词决策与执行硬隔离）和 `teams/storyboardTeam`（导演/编写/审阅分工）可以归纳出三层职责（本文归纳，非官方表述）：

| 层级 | 对应 Toonflow 实现 | 职责 | 权限边界（源码可证） |
|---|---|---|---|
| 决策层 | workflow/SKILL.md 主流程 + PART A | 理解意图、拆解任务、产出定稿提示词 | 「提示词硬隔离」：定稿前不碰画布，执行层不得改写已定稿的分段/剧情/站位/运镜 |
| 执行层 | storyboardTeam（导演→编写）+ canvasExecution.md | 文字分镜编写、连接真实参考、写入生成节点、启动媒体生成 | 只做委派工作；成员不递归互相委派；须先取得算力授权并「临执行复核」 |
| 监督层 | reviewer 成员 + 连续性知识 | 审阅产出、指明镜头/依据/最小修改建议 | 不代执行、不替用户批准生成、不调用消耗算力的工具、不改画布文件 |

> 对移动端的启示：**决策层 = 编排流水线的「主编排 Agent」，执行层 = 各阶段专职 Agent（编剧/导演/资产/分镜），监督层 = 审校 Agent**。移动端可以把这个协作关系简化为一条**有状态机的 Pipeline**，每个阶段一个专职 Agent。

### 2.3 借鉴它的 Skills（技能）体系

Toonflow 的「智能」本质上是一组 **Markdown 技能文件 + 工具调用**，核心在 `packages/skills/` 与 `packages/teams/`：

| 技能/文件 | 职责 | 对本项目的借鉴 |
|---|---|---|
| `workflow/SKILL.md` | 制作工作流主入口：输入判定 → 剧本 → 资产 → 分镜 → 生成 | **Pipeline 主流程** |
| `workflow/references/sourceAndScript.md` | 输入与剧本：小说改编、创意写剧本、定稿剧本提取 | **「小说 → 剧本」阶段** |
| `workflow/references/methods/storyDevelopment.md` | 故事开发：命题、人物、因果、代价选择 | **「AI 写小说」阶段（与 InkOS 结合）** |
| `workflow/references/methods/screenAdaptation.md` | 剧本改编：视听化、场景任务、对白、信息差、节奏 | **「小说 → 剧本」核心方法论** |
| `workflow/references/assets.md` | 资产：角色四视图板、场景主视图、道具 2×2 板 | **「资产图片」生成规范** |
| `workflow/references/methods/visualDesign.md` / `colorAndLight.md` | 视觉设计、色彩用光 | 资产与分镜画面风格 |
| `workflow/references/canvasExecution.md` | 画布执行、真实引用绑定、生成授权 | **「执行层」与算力授权** |
| `workflow/references/stateAndDelivery.md` | 状态与交付、版本记录 | **本地版本管理** |
| `canvas/SKILL.md` | 画布节点操作手册 | 移动端替换为**结构化数据操作** |
| `teams/storyboardTeam/` | 导演/编剧/审阅 + 连续性知识 | **分镜阶段的三角色协作** |

其中 `workflow/SKILL.md` 内嵌了 Seedance 视频导演的 **PART A 执行规则（A0–A12）**，是「剧本 → 分镜 → 视频提示词」的最核心方法论，要点：

- **A0 剧情保真锁**：只导演，不编剧。禁止新增/删除/替换/改归属/改顺序/改因果。
- **A1 资产命名与参考绑定**：角色/场景/道具用稳定标识，参考图绑定到每个生成段。
- **A2 全量节拍解析**：把剧情拆成完整、连续、可计时的原子节拍（对白/动作/反应/信息/过渡），全部登记，建立「源剧情账本」。
- **A3 分段与时长预算**：按对白自然语速 + 动作时间估算单段时长，先全片规划再分批交付。
- **A4 资产与出镜状态**：每个角色/场景/道具按时间轴登记出镜状态。
- **A5 站位双层坐标**：世界坐标（轴线地标）+ 画面坐标（当前机位），每段自包含。
- **A6 表演层**：情绪是行为的副产品，微表情必须有源剧情依据。
- **A7 运镜与段间衔接**：相邻独立生成段至少满足主体/景别/角度中一项差异，避免「错误续帧」。
- **A8 跨段连续性检查**：人物位置、道具状态链、场景物理环境连续性。
- **A9 分段提示词模板**：按模型路由输出最终可投喂的生成提示词。

### 2.4 借鉴它的 Provider 抽象

Toonflow 通过 `packages/providers/` 统一接入模型，核心发现：

- **LLM**：`protocol: "openai-completions"`（OpenAI 兼容协议，DeepSeek 等均走此协议）。
- **媒体**：图片/视频/音频供应商（tfRouter、apiMart、meta）。
- **AI 调用**：`apps/server/src/utils/ai/index.ts` 用 `@earendil-works/pi-ai` 做协议抽象（openai-completions / openai-responses / anthropic-messages），支持流式输出、多模态参考（图片 base64）。
- **Agent 运行时**：`apps/server/src/agent/runtime/subAgent.ts` 用 `@earendil-works/pi-coding-agent` 做 Agent 会话与子 Agent 委派。

> 对移动端的启示：**LLM 统一走 OpenAI 兼容 `/chat/completions` 协议 + SSE 流式**，这是移动端最容易对接的方式；图片/视频生成走各供应商的异步任务 API（提交任务 → 轮询/回调取结果）。移动端需要自建一个轻量 `ProviderAdapter` 抽象层，而不是依赖 `pi-ai` 这类 Node 库。

## 3. AI 写小说借鉴分析（InkOS 为主）

### 3.1 为什么选 InkOS

调研了多个 AI 写小说开源项目后，选定 **InkOS**（TypeScript，多智能体流水线）作为主要参考，理由：

- 它解决的核心痛点与本项目一致：**长篇创作的角色失忆、伏笔断线、文风突变**。
- 它把写作拆成可审计的工程化流水线（写手/审计员/修订员），而非「单次 prompt 生成一段文字」。
- 它有 **Truth Files（真相文件）** 机制，解决长期记忆/一致性。

同时参考其思路但**做移动端适配裁剪**（见第 5 节）。

### 3.2 InkOS 核心机制

**多智能体协作（README 官方职责表 + `src/agents/` 源码）：**

| Agent | 职责 |
|---|---|
| Radar 雷达（可插拔） | 扫描平台趋势和读者偏好，指导故事方向 |
| Planner 规划师 | 读取作者意图 + 当前焦点 + 检索结果，产出本章意图（must-keep / must-avoid） |
| Composer 编排师 | 按任务从结构化状态、控制文档和材料中选择上下文，记录保护层级、检索与压缩轨迹 |
| Architect 建筑师 | 建书/导入时生成基础设定：故事框架、规则、角色与长期控制文件 |
| Writer 写手 | 基于编排后的精简上下文生成正文（字数治理 + 对话引导） |
| Settler 状态结算 | 通过 typed tool 提交正文有证据的增量 state delta，由宿主校验并原子落盘 |
| 审稿 Agent | 对照用户意图、正典、状态、章节计划，返回有证据的定性观察 |
| Reviser 修订者 | 接受明确修改目标，生成并原子落盘新版本 |
| 连续性审计员 | 对照状态文件检查每章草稿的一致性（角色「记起」没见过的事、拿出已丢失的武器等） |

**真相与状态机制（`story/` 目录，源码可证）：**

| 层 | 内容 |
|---|---|
| 权威结构化状态 `story/state/*.json` | `current_state.json`（SPO 事实三元组，带生效章节区间 validFrom/validUntil 与来源章）、`hooks.json`（伏笔钩子：open/progressing/deferred/resolved/superseded 五状态 + 预期回收）、`chapter_summaries.json`（章节/人物/事件/状态变化/钩子活动/情绪/章节类型）、`manifest.json`；均经 Zod schema 校验 |
| 人类可读投影 `story/*.md` | `current_state.md`、`pending_hooks.md`、`chapter_summaries.md`、`character_matrix.md` 等（由权威 JSON 渲染，只读） |
| 控制文档 | `story/author_intent.md`（这本书长期想成为什么）、`story/current_focus.md`（近 1–3 章要把注意力拉回哪里） |
| 每章运行时 `story/runtime/` | `chapter-XXXX.intent.md`（本章目标/保留项/避免项）、`context.json` 与 `trace.json`（实际进入模型的上下文与编译轨迹） |
| 检索投影 `story/memory.db` | 可重建的 SQLite FTS5/BM25 索引，**不作为故事事实权威** |

关键设计：正文与状态作为同一组产物**原子落盘**；Settler 只提交有证据的增量 delta，代码层做 immutable apply；「资源/支线/情感弧线」等没有独立文件，统一用事实三元组（current_state）与摘要行（mood/chapterType）表达。

**Revision modes（修订模式，CLI 可证）**：`spot-fix`（定点修）、`polish`（润色）、`rewrite`（重写）、`rework`（结构重组）、`anti-detect`（去 AI 味，由可替换的 deslop Skill 提供）。

> 对本项目的启示：借鉴「权威 JSON 状态 + 人类可读投影 + 事实三元组带章节有效期 + typed delta 原子落盘」的思路，把它简化为**本地数据库状态表（本项目定义为 7 类：世界事实、角色矩阵、资源与道具、伏笔钩子、章节摘要、作者意图、当前焦点）**。写作时只注入相关片段；每章定稿后由固化步骤提交状态增量；审校时对照状态表查一致性。7 类的划分是本项目对 InkOS 机制的移动端裁剪。

## 4. 两套流程的整合方案

Toonflow 擅长「剧本 → 镜头」，InkOS 擅长「创意 → 小说」。整合后的完整链路：

```text
┌─────────────────────────────────────────────────────────────────┐
│                    创意 / 一句话 / 已有小说原文                    │
└──────────────────────────────┬──────────────────────────────────┘
                               ▼
                 ┌─────────────────────────┐
                 │  阶段 A：AI 写小说        │ ← 借鉴 InkOS
                 │  世界观 / 角色 / 大纲 /    │   Planner + Writer
                 │  逐章正文 / 审校 / 固化    │   + Truth Files
                 └────────────┬────────────┘
                              ▼
                 ┌─────────────────────────┐
                 │  阶段 B：小说 → 动漫剧本  │ ← 借鉴 Toonflow
                 │  结构化改编 / 视听化 /     │   sourceAndScript +
                 │  场次对白 / 忠实度检查     │   screenAdaptation
                 └────────────┬────────────┘
                              ▼
                 ┌─────────────────────────┐
                 │  阶段 C：提取剧本骨架     │ ← 借鉴 Toonflow A2
                 │  节拍 / 场景 / 角色 / 道具 │   全量节拍解析
                 │  分段 / 时长 / 出镜状态    │
                 └────────────┬────────────┘
                              ▼
                 ┌─────────────────────────┐
                 │  阶段 D：生成动漫资产图片  │ ← 借鉴 assets.md
                 │  角色四视图 / 场景主视图 / │   视觉设计 + 色彩用光
                 │  道具多视图               │
                 └────────────┬────────────┘
                              ▼
                 ┌─────────────────────────┐
                 │  阶段 E：生成动漫镜头     │ ← 借鉴 PART A A4-A9
                 │  分镜提示词 / 参考绑定 /    │   站位 / 表演 / 运镜 /
                 │  生成图片或视频            │   连续性 / 提示词模板
                 └─────────────────────────┘
```

各阶段都产出**可持久化、可编辑、可回溯**的结构化数据，用户可在任意阶段人工介入修改后继续。

## 5. 移动端适配裁剪（关键决策）

Toonflow 是桌面端无限画布 + 可视化节点，移动端必须裁剪：

| Toonflow 桌面能力 | 移动端裁剪方案 |
|---|---|
| 无限画布自由编排节点 | 改为**结构化列表/时间轴视图**（剧本 → 分镜 → 资产的线性流程 + 可点开编辑） |
| 可视化节点连线 | 改为**数据引用关系**（分镜引用资产 ID、参考图句柄），无需拖拽连线 |
| `canvas/SKILL.md` 画布工具 | 替换为**本地数据库 CRUD 工具**（Agent 直接读写结构化实体） |
| Agent 运行时 `pi-coding-agent` | 自建轻量 **Pipeline 编排器 + 阶段状态机**（移动端无 Node 运行时） |
| 文件系统工作区 | 本地 **SQLite + 文件目录**（资产图片存本地，元数据存 DB） |
| 模型供应商 `pi-ai` | 自建 **ProviderAdapter**（LLM 走 OpenAI 兼容 SSE，媒体走异步任务 API） |
| 桌面端 Electrobun 桌面壳（本地服务 + Web 视图） | 单进程移动 App（Dart/Flutter 或 Kotlin） |

**核心结论：移动端保留 Toonflow 的「Skills（Prompt 方法论）与流水线思想」，丢弃「画布/节点/桌面壳」，用本地数据库 + 结构化数据流替代。**

## 6. 技术选型

### 6.1 推荐：Flutter

| 维度 | 说明 |
|---|---|
| 平台 | Android APK 为主，未来可扩展 iOS，单代码库 |
| 语言 | Dart，强类型，适合复杂业务建模 |
| 状态管理 | Riverpod（推荐）或 Bloc |
| 本地存储 | Drift（SQLite ORM，类型安全）或 Isar；资产文件存应用私有目录 |
| 网络 | Dio + SSE 流式（LLM 流式输出） |
| 编辑器 | flutter_quill（富文本/Markdown 小说编辑器） |
| 图片 | cached_network_image（本地文件 + 网络图缓存） |
| 视频 | video_player（镜头预览） |
| 分镜展示 | 自绘 ListView/GridView + 可选时间轴 |

**选择理由：**
1. 移动端复杂 UI（编辑器、分镜列表、资产网格、流式对话）生态最成熟。
2. 单代码库覆盖 Android/iOS，符合「手机 APK 本地端」定位。
3. 状态管理与数据层能力强，适合本项目「多阶段流水线 + 结构化数据」的复杂度。
4. 性能优于 React Native，开发效率优于 Kotlin 原生。

### 6.2 备选方案

| 方案 | 优势 | 劣势 |
|---|---|---|
| Kotlin + Jetpack Compose | Android 原生性能最佳 | 仅 Android，开发效率略低 |
| React Native / Expo | 与 TS 参考项目技术栈一致 | 复杂编辑器/长列表性能、生态不如 Flutter |
| Flutter（推荐） | 见上 | 需学习 Dart |

> **技术栈已确认：Flutter。**

### 6.3 AI API 端点方案

- **LLM 文本**：OpenAI 兼容 `/v1/chat/completions`（支持 DeepSeek、通义、Kimi、智谱、OpenAI 等任意兼容端点），SSE 流式输出。
- **文生图 / 图生图**：优先选支持 OpenAI Images 兼容协议或 gpt-image 类供应商；也支持自定义异步任务供应商（提交 job → 轮询结果）。
- **文/图生视频**：借鉴 Toonflow 的 Seedance 接入思路，走供应商异步任务 API（提交 → 轮询），App 内做任务队列与结果回填。
- **用户自配**：App 内置「模型供应商配置」页面，用户填入 Base URL + API Key + 模型名，与 Toonflow 的 `customProviders` 机制一致。

## 7. 已确认的关键决策（用户拍板）

| 决策点 | 结论 |
|---|---|
| 技术栈 | **Flutter** |
| 镜头产物形态 | **分镜图 + 视频都要**（先出分镜图供确认，再对确认镜头生成视频） |
| AI 写小说自动化程度 | **人机协作**（每章生成后人工确认/修订再进入下一章） |
| 里程碑范围 | **直接含视频**（M0–M7 全部执行，视频为核心交付而非后置选项） |

> 影响：开发计划按「全量交付（含视频）」推进，M6 视频生成为核心里程碑；M5 分镜图仍是视频前必经的确认节点。

### 9.1 「分集」的真实形态

集是**叙事总量单位**，无 episode id、无集序号字段、无集级状态机。「集」相关表述只有三处：叙事规模判定（单场戏 / 短集 / 2–3 分钟甚至更长的整集）、示例（一集 180s）、以及多集在项目内各自子目录保存生产状态文件。全局段号 `G01/G02...` 才是真正的执行单位，一段 = 一次生成 = 一份提示词 = 一个视频节点。`Batch` 是纯交付容量分批，明确写「批次边界只影响一次输出多少段，不改变全片顺序、段号和连续性」。

### 9.2 时长约束的完整数字

| 项 | 值 |
|---|---|
| 单段硬上限 | Seedance 2.0 ≤ 15s；2.5 ≤ 30s |
| 理论最少段数 | `⌈总时长 / 单段上限⌉`，只作下限 |
| 单批交付上限 | 2.0 最多 6 段；2.5 最多 3 段 |
| 节拍最低时长 | 自然对白时间 + 必要停顿 + 必须串行动作 |
| 呼吸余量 | 不确定时留 10%–20% |
| 单段镜头密度 | 2.0 通常 1–2 个（最多 3）；2.5 通常 2–4 个 |
| 微表情事件 | ≤15s 段 1–2 个；16–30s 段 2–3 个；0 个允许 |
| 段间衔接 | 景别差 ≥ 2 档 或 角度差 ≥ 90° |
| 每段时间码 | 一律从 `00:00` 重新开始 |

### 10.1 最关键的发现：产物文件覆盖写，版本历史形同虚设

这是本轮唯一属于「已交付功能实际失效」的缺陷，且横跨两个已验收的里程碑：

- `AssetFileStore.save`（`lib/core/storage/asset_file_store.dart:19`）固定写 `files/assets/asset_${assetId}.png`；`ShotFileStore.save`（`shot_file_store.dart:19`）固定写 `files/shots/shot_${shotId}.png`；`VideoFileStore.save`（`video_file_store.dart:19`）固定写 `files/videos/shot_${shotId}.mp4`。三者都是**同名覆盖写**。
- 而 M14 T16.6 建的 `ShotRevisions` / `AssetRevisions` 快照表，以及 M8 的视频多任务机制，都把 `imagePath` / `outputPath` 存进快照。由于每次生成都覆盖同一个文件，**所有历史快照指向同一个路径，指向的都是最新一次生成的字节**。
- 后果：`shot_detail_page.dart:876` 的 `_HistoryVersions` 面板会列出多个版本，但每一行的路径相同，「切换到旧版本」重新指向的仍是新文件——用户看到的是最新版本。**资产图侧连这个面板都没有**（`assetRevisionsProvider` 已建但全库零调用方）。
- 根因是文件命名，不是 UI 或 DAO：`RevisionDao` 的快照事务与状态机都是对的，失效点在落盘层。修 UI 等于给坏轮子加外壳。

对齐参照：Toonflow `packages/nodeScaffold/src/components/mediaHistory.vue` 的历史是「每个生成结果一条独立记录 + 分页 20 条 + 设为当前」，其前提是每个结果有独立存储地址。

### 10.2 采纳清单（M17）

1. **产物文件版本化落盘（根因修复）**：三个 file store 的 `save` / `saveFromPath` 改为带时间戳的唯一文件名，新产物不再覆盖历史字节。无 schema 变更——`Shots.outputPath` / `Assets.imagePath` 已存绝对路径。
2. **资产图历史版本切换 + 本地替换**：`AssetService.selectImageVersion` / `replaceImage`，`AssetFileStore.saveFromPath`，详情页新增历史面板。补上 `assetRevisionsProvider` 的调用方。
3. **分镜图历史版本切换 + 本地替换**：`ShotService.selectImageVersion` / `replaceImage`，`ShotFileStore.saveFromPath`，分镜图 Tab 新增同型面板。
4. **生成尝试台账查看页**：M14 T16.5.4 已把提示词/参数/引用/授权指纹/失败原因全部写入 `GenerationAttempts`，但**全库无一处 UI 读取它**（仅 `listBySubject` 供内部比对，未暴露）。补 `listByProject` + 台账页，让「钱花在哪、失败为什么、当时用的什么提示词」可查。对齐 Toonflow `canvasExecution.md` 的生成尝试台账与 `stateAndDelivery` 的采用记录。
5. **章节目标字数可配置 + 定稿字数门槛**：`chapter_editor_page.dart:266/295/361` 三处硬编码 `targetWords = 2000`，与作品实际体感无关。`NovelBooks` 新增 `targetWords`（默认 2000），定稿前跑下限 0.8× / 上限 1.3× 门槛。对齐 InkOS `packages/core/src/utils/length-metrics.ts:56` 的 `chapterLengthDelivery`（`needs_revision` 判定）与 `assertChapterLength`（抛 `CHAPTER_LENGTH_OUT_OF_RANGE`）。

它的核心设计是一句话：**能检查的东西全部落到脚本里，不靠提示词碰运气**。五段管线共 52 道质量门（大纲 14 / 美术 10 / 剧本 10 / 分镜 18），全是纯函数校验，零额外 LLM 调用，在消耗算力之前拦下。

最有价值的四条可直接移植：

1. **同批角色提示词雷同检测**（`novel-characters.mjs:508-530`）。按词集合算 Jaccard 相似度，阈值 0.75，超了点名那一对并给出百分比。**阈值是量出来的不是拍的**：自带样例四个角色两两最高 39%，而「只改年龄与衣服颜色」的雷同用例是 98%，中间余量极大。它同时写清了一个反例——`image.sheet` 刻意不查，因为三分区排版规范本身是大段固定文本，真实角色之间本来就有 63% 重合，**误拦的门比没有门更糟**。
2. **确定性时长引擎**（`novel-script.mjs:22-48`）。台词秒数 = 非空白字符数 ÷ 语速（`charsPerSecond: 4.5`，中文口语偏快档），动作节拍按固定秒数计（`actionSeconds: 2.5`），容差 ±15% 可配。**是估算不是秒表**，但一集写到五分钟的剧本会在这层被拦下，不会流到生成环节才发现。附一条 `maxLineChars: 35`——一口气说不完的台词也生成不了。
3. **提示词永远空景、禁人、禁角色名**（`novel-art/references/scene-pass.md:32`）。场景参考图里必须明写 `empty scene / no people`，`negativePrompt` 必须禁人，**绝不出现角色名、作者名、作品名**——图像模型会把它认识的东西画进去。道具侧是「白底、无人、无手」，反向提示词必须禁 `hands/fingers`（拿着道具的手是最常见的污染）。这三条都能变成纯文本校验。
4. **提示词不写渲染风格**（同文件 `:34`）。不要出现 `Semi-realistic environment concept art` / `painterly rendering`，也不要给 tags 打 `semi-realistic` / `painterly`。画风是出图那一刻才定的，整批共用一段风格指令由调用方附加——写进每条提示词只会跟当时选的风格打架，换风格还要逐条改。本项目已用 `effectiveArtStyle` 做了这件事，缺的是**反向校验**。

工程约定两条也值得抄：

- **门 id 保持稳定不动**——它是日志与下游对账的凭据（`novel-outline.mjs:182`）。对齐本项目 `ReviewIssue.code` 稳定机器码约定，说明这条判断是被独立复现的。
- **缺字段的旧数据照常通过，门明说跳过而不报错**（同文件 `:191-194`）：「没有 props 字段的旧大纲要照常通过，否则每一份存量 outline.json 一升级就全红」。这正是本项目新增值类型（`variantOf`、集时长预算等）该守的向后兼容原则。
- **失败累积留痕**：`.gates.jsonl` 记录每次 `validate` / `checkup` 的失败门，可回看哪份文档哪次失败。本项目 `GenerationAttempts` 只覆盖生成侧，本地校验失败目前不留痕。

还有一条流程能力：**体检模式**——已有大纲可以只跑检查不重新生成。本项目已有同型能力（`ShotService.listTransitionIssues`），可推广到骨架与剧本。

### 11.3 AIComicBuilder：迁移文件即领域能力清单

55 条 Drizzle 迁移的文件名串起来，就是一份「小说转动画」领域的结构化字段路线图，其中五条本项目完全没有：

| `0018` / `0019` | `dialogue_start_ratio` / `dialogue_end_ratio` | 台词在镜头内的起始/结束时间窗，决定观感 |
| `0020` / `0021` | `shot_is_stale` / `character_is_stale` | 上游改了下游自动标失效——本项目 docs/02 §7「影响面」缺的具体落地形态 |
| `0022` | `episode_script_hash` | 阶段哈希：上游剧本变了就重跑下游 |
| `0028` `0034` `0035` `0036` `0037` | `composition_guide` / `focal_point` / `depth_of_field` / `sound_design` / `music_cue` | 镜头从「一段自由正文」升级为结构化字段，可控性差异很大 |

### 11.4 goink：写完一章自动注入维护提醒

`internal/mcp_tools/rw_tools.go:431` 的判断只有三个条件：不是大纲、`change_type == "full_replace"`、正文超过 500 字——满足就向会话注入一条 user 消息，要求更新角色设定、故事时间线（伏笔回收/新伏笔/章节计划）、读者认知、弧线节点进度，然后汇报摘要。

本项目已有更结构化的 Settler 固化（事务 + 乐观锁 + 状态机），机制上更强。这条的价值在**时机**：Settler 是「定稿时才跑」，而这里是「正文一落盘就提醒」，中间的空档正好是作者忘了更新设定、下一章基于残缺真相继续跑的时候。低成本，可排。

### 11.5 提示词实测规则（可直接抄进 skill）

来自 `character-refs/references/prompting.md`（100 行，每一条都注明是某一轮实测失败换来的）与 `novel-storyboard/references/shot-writing.md`（75 行）。选最值得进本项目的：

**角色参考图（四视图/大头照/侧面/背面/细节）**

1. **改图模型只听第一句**。参考图的构图力量很强，模型默认照参考图重画一张差不多的，只有第一句明确要求改构图它才改。大头照第一句必须是 `Zoom in to an extreme close-up head-and-shoulders portrait, passport-photo framing`，再写可量化取景（头顶贴近上边、下巴在画面高度正中、下边切在锁骨）；只写 `close-up` 会出成半身。
2. **正面也要写成几何**。「肩、髋、脚都正对镜头，鼻子在脸的中线上，两只耳朵一样可见」+ 反向禁 `three-quarter view` / `turned body` / `contrapposto`。只写 `facing the camera` 时，**动漫画风会按「官方角色图」的习惯把锚点画成微侧身，大头照照着锚点改，也跟着侧过去 20–30°**，几乎和 45° 那张一样。取景写在几何前面、结尾再重申一次。
3. **一致性清单要短，按视图取层**。不要把锚点的长描述整段重复进派生图。大头照只写脸、头发、上装——**写了下装和鞋，模型就把镜头拉远去画它们**（实测：带上全部服装和四个细节，大头照出成了半身）。细节图不列整套服装，只写 `Same person, same clothing and materials as in the reference image`——第一轮细节图 8/8 失败就是因为列了整套衣服。
4. **背面写只有背面看得到的东西**（辫子垂在背后、衣服背面、脚跟），反向禁 `face` / `buttons` / `pockets`；不写这些 Qwen 会出成正面。
5. **不写 `model sheet` / `turnaround` / `character sheet`**——这几个词会让模型在一张图里画多个视图，反向词里还要专门压 `character sheet` / `multiple views`。
6. **一张图只参考锚点，图与图之间不链式参考**——链式会累积漂移，也会让单张重出牵连一串。大头照缺失或过期时退回只挂锚点，不阻塞。
7. **多人同框绝不用拼接参考图**。每人一张「大头照 + 三视图」拼接图，4 张里 3 张画出 3–4 个人（拼接图里的每个视图被当成一个人），而且女主被男主吃掉。只有「女主大头照 + 锚点、男主锚点」这组 4/4 全对。
8. **细节图露出的皮肤要补年龄**。领口、袖口、鞋三类细节加一句 `Any visible skin is the skin of a 16-year-old.`（年龄取角色字段）——Qwen 画这些部位时没有脸做参照，年龄感会丢。
9. **写光的效果，不写光源**——写 `window` 会把窗户画进画面。
10. **皮肤粗糙程度不放画风层**，放角色字段：统一写「泛红、小瑕疵」会让年轻角色出成病容。

**分镜正文**

11. **一切一个主运镜，不叠加**。推完再摇、边跟边环绕，模型只会挑一个做，还未必是你要的那个。
12. **动作要能在这几秒内做完**。挑担上船、搭手卸担、抬头看向岸边这类模型见过千万次的动作；精确的物理交互、微表情、手指的细小动作不要写——写了也不会被画对，只会挤掉真正要演的那一下。**优先低缓连续的小动作**，狂奔、大跳、剧烈翻滚尽量规避。
13. **情绪外化成身体细节**：悲伤是低头、肩膀微颤、手指攥紧衣角；紧张是频繁看表、手指敲桌、眼神闪躲；愤怒是双拳紧握、下颌绷紧、胸口起伏。不写「很悲伤」。
14. **视频侧不写角色姓名，用通用身份**（「一名铁灰袍中年男子抬头看向门口」），姓名只许出现在台词原文里。**分镜图侧恰好相反**——要直呼其名，因为那里挂着角色参考图。两侧的规矩不一样，因为两侧的规范不是同一个人定的。这条最容易做反。
15. **构图要量化，不能只写景别**。纯参考图出片时没有那张图，景别偏远、动作偏小、人物摆位随意，消失的正是这些信息。要显式给：焦距 + 景深、机位（对着谁 + 什么角度）、构图（三分法/中心/对角线/对称）、视线落点、焦点、稳定性，段级再给 `blocking`（开场那一瞬谁在画面左、谁在右、面朝哪、相距多远，用厘米或步数）。
16. **参考图只锁身份，不锁构图**。人物、场景、道具的参考图用来锁身份、脸型、服装、场景结构、道具造型；正文不要照搬参考图的构图、排版、视角。
17. **不新增剧本没有的人物、道具、动作、对白、画面上的可见文字**。分镜是资产合成，不是凭空画。
18. **不写朝代之外的年代词**。「古代」「古装」不是画面；服制、器物、建筑形制才是，而这些已经在设定图里定了。

**场景与设定**

19. **先定朝代，再写场景**，整部剧一个具体的真实朝代写进文档级 `dynasty`。不许写「古代」「古装」「某朝」「架空」——它们在画面上没有任何对应物，模型读到「古代府邸」只能自己挑，于是庭院出成宋、书房出成明、道具出成清，摆在一起不像同一部戏。原著是架空设定就写它**像**哪个朝代（`明代风格`）。
20. **表面处理两档二选一，别把「日常使用」当默认**。金銮殿会出成漏雨的废殿——实测里 S06 金銮殿拿到了「漆面剥落」和「门框下部有浅淡水渍」，那是全国维护最勤的一栋建筑。这是把一个该按对象决定的事实写成了一句对谁都成立的常量。
21. **锚点要「可画、可认、可核对」**。好锚点：补丁船篷、断裂的第七块桥板、绿锈铜铃——生成图里一眼找得到，缺了立刻发现。坏锚点：「陈旧的氛围」「岁月的痕迹」——没法核对的不是锚点是形容词。
22. **能做变体就别开新景**。AI 生成一个新环境很便宜，但每多一个独立环境就多一份一致性维护。改时段、换天气、换前景、删道具用 `variantOf` 挂到母场景上，桥板细节这类资产直接复用。

### 11.6 明确不采纳

- **架构层**：这一批项目全部是 Web/桌面 + 自建后端 + PostgreSQL + 自建 Agent SDK。本项目是 Flutter 单端 + SQLite + 云端 API，架构差距不在同一量级，全部不采纳，只取规则与字段。
- **StoryDiffusion 一致性自注意力**：需 GPU 20GB+，本机不具备，且本项目文生图走云端供应商。其「锚点帧锁定」思路已由 §11.5 第 7 条与本项目四视图参考板覆盖。
- **提示词 12/16 插槽 + 三级覆盖的完整实现**：产品差距最大，但需要新增提示词管理表、编辑器 UI、覆盖解析层，改动面超过一轮。本轮只把它登记为任务（docs/04 T21.9），实现另起里程碑。
- **prompt_ab_tests**：需要同一提示词并行跑两版再人工比对，移动端算力与存储都不适合，列入 backlog。
- **Comic Sol / OpenManga 的确定性排版与漫画多格合成**：本项目路线是「分镜图 → 视频」，不走漫画页排版，无对应交付面。

### 11.7 结论

三轮内部复研已经把方法论层收敛了；这一轮 GitHub 对标的价值在于**别人已经把失败案例写成了代码注释**——Jaccard 0.75 那个阈值是量出来的、细节图 8/8 失败是跑出来的、金銮殿出成废殿是实测出来的。把「能本地机械校验的规则进代码、需要判断的规则进 skill prompt」这条既定原则（§9.3）应用到这批规则上，能拿到一批**零 LLM 成本、在消耗算力之前拦截**的质量门，以及一批直接可用的提示词实测规则。任务拆解见 docs/04 §8.cc。
